## Aprendizados técnicos

- `StorageTarget` generalizou `AzureTarget` (migração `000005_storage_targets`): suporta `azure`, `s3` e `filesystem`, discriminado por `Type`, com `CHECK` constraints por tipo. `azure_targets` e `servers.azure_target_id` foram mantidos (não removidos) como rede de segurança pós-migração.
- O AAD (additional authenticated data) do AES-256-GCM do SAS token do Azure é `id + ":" + "sas_token"` — por isso a migração 000005 preservou exatamente o `id` de `azure_targets` ao copiar para `storage_targets`. Mudar esse `id` invalidaria permanentemente tokens já criptografados.
- Nome do cookie de sessão não é fixo: é configurável via `SESSION_COOKIE_NAME` (default `backapeando_backup_session`).
- **Bug de causa raiz não óbvia (2026-09-15): `repository.BackupRunRepo.UpdateStatus` nunca persistia `started_at`/`finished_at`.** É o único mecanismo de transição de status usado por todo `internal/scheduler` (`executor.go`, todas as finalizações; `scheduler.go` na promoção `queued→running`), mas sua query só tinha `status`/`error_message` no `SET`. Resultado: toda run processada pelo scheduler (agendada via cron OU manual via `/run-now`) ficava com `finished_at=NULL` para sempre; runs manuais assíncronas também ficavam com `started_at=NULL` para sempre. Só o caminho síncrono `BackupNow` (que usa `Create`/`MarkSuccess`/`MarkFailed`, não `UpdateStatus`) estava correto. Corrigido fazendo `UpdateStatus` setar `started_at = COALESCE(started_at, now())` quando `status="running"` e `finished_at = now()` quando `status` é `"success"`/`"failed"`, sem tocar nenhum call site em `executor.go`/`scheduler.go`. **Armadilha para o futuro:** qualquer novo método de transição de status em `backup_runs` precisa decidir explicitamente o que fazer com esses dois timestamps — não é automático, e o teste antigo (`executor_test.go`) não pegava isso porque seu mock nem modelava os campos.
- Nomes de constraint únicos do Postgres (`admin_users_email_key`, `admin_users_cpf_unique`) são usados em `admin_users.go` (handler) para mapear violação de unicidade (`pgconn.PgError`, code `23505`) para `409` com mensagem específica (e-mail vs. CPF). Se uma migração futura recriar essas constraints com outro nome (`DROP`+`ADD CONSTRAINT` sem preservar o nome), o mapeamento cai silenciosamente no branch `default` ("duplicate value", ainda correto, só menos específico) — não quebra, mas perde precisão.
- **Segunda ocorrência do padrão "AAD (associated data) divergente entre encrypt/decrypt" (2026-09-15, suporte multi-engine):** a primeira ocorrência foi o SAS token do Azure (linha acima). Ao adicionar `Server.DBPasswordEncrypted`, criei uma única constante compartilhada `domain.DBPasswordAAD = "db_password_encrypted"` (em `backend/internal/domain/domain.go`), importada tanto no lado de encrypt (`httpapi/handlers/servers.go`, `Create`/`Update`) quanto nos lados de decrypt (`scheduler/executor.go`, `httpapi/handlers/backup.go`) — nunca um literal de string repetido em cada call site. Qualquer novo segredo criptografado com `crypto.Sealer` deve seguir o mesmo padrão (constante única, não string literal duplicada), porque um AAD divergente falha a decriptação silenciosamente (retorna `ErrDecryptFailed`, não um erro que aponte para "AAD errada").
- **Armadilha real encontrada ao montar comandos remotos multi-engine:** `docker exec <container> NOME=valor comando` **não** funciona como atribuição de variável de ambiente — `docker exec` não interpreta a sintaxe de atribuição do shell, e trataria `NOME=valor` como o próprio nome do binário a executar dentro do container (erro "executable file not found"). O jeito correto é usar a flag própria do Docker: `docker exec -e NOME=valor <container> comando`. Em modo "host" (sem Docker), a sintaxe de atribuição de shell (`NOME=valor comando`) funciona normalmente porque nesse caso o processo sendo exec'd é de fato o primeiro argumento do shell. Ver `backend/internal/scheduler/dumpcommand.go` (`assembleRemoteCommand`) — os dois casos são tratados por ramos separados, não por uma única string concatenada.
- **`ui/select` (reka-ui/Radix) precisa de shim de pointer-capture para rodar em `happy-dom` (o ambiente de teste deste projeto), e mesmo com o shim, simular abertura+clique do popover teleportado não seleciona o item de forma confiável** — limitação conhecida de testar Radix fora de um browser real (pointer capture, foco, roving tabindex). `frontend/src/test/setup.ts` (novo) faz o shim mínimo (`hasPointerCapture`/`setPointerCapture`/`releasePointerCapture`/`scrollIntoView`), registrado via `vitest.config.ts` → `test.setupFiles`. O padrão de teste que funciona de forma confiável é interagir diretamente com o contrato `v-model` do componente: `wrapper.findAllComponents(Select)[i].vm.$emit('update:modelValue', valor)` — testa a reatividade real do template sem depender da simulação de pointer/teclado do Radix. Ver `ServerNewView.spec.ts`/`ServerEditView.spec.ts`. Correlato ao achado já registrado acima sobre `ui/dialog`/Teleport.
- **Bug crítico encontrado pelo Validator nesta mesma tarefa (2026-09-15): um `CHECK` condicional-por-coluna (`servers_password_required_by_engine`, migração `000006`) quebra o padrão pré-existente de "INSERT sem o segredo, depois UPDATE do segredo criptografado" usado para a chave SSH.** `repository.ServerRepo.Create` fazia `INSERT` sem `db_password_encrypted` (só preenchido depois via `SetDBPassword`, porque o AAD da criptografia depende do `id` gerado pelo banco) — mas o `CHECK (db_engine = 'postgres' OR db_password_encrypted IS NOT NULL)` é avaliado no próprio `INSERT`, então toda criação de servidor `mysql`/`sqlserver` falhava com `SQLSTATE 23514` antes mesmo de `SetDBPassword` rodar. Só foi pego porque o Validator rodou `TestSetDBPassword` contra um Postgres real — os 196 testes unitários "passando" nesta sessão não incluíam nenhum teste com `DATABASE_URL`. Corrigido gerando o `id` do servidor no lado Go (`uuid.New()`) _antes_ do `INSERT`, para poder criptografar a senha com esse `id` como AAD e incluir `id`+`db_password_encrypted` no mesmo `INSERT` (`repository/servers.go Create`, `httpapi/handlers/servers.go Create`). **Armadilha para o futuro:** qualquer nova coluna criptografada cujo `CHECK`/`NOT NULL` seja condicional a outro campo (não incondicional, como a chave SSH) não pode seguir o padrão "insere sem o segredo, decide o AAD depois com o ID gerado" — o ID precisa ser gerado no lado da aplicação antes do `INSERT` nesses casos.
- **Flakiness conhecida na suíte de integração (achado pelo Validator, 2026-09-15): rodar `go test ./...` com `DATABASE_URL` setado, sem `-p 1`, causa contenção cruzada entre pacotes que compartilham o mesmo banco** (`internal/httpapi/handlers` teve `TestAdminUserHandlers_*` falhar de forma transitória em paralelo, mas passar isoladamente ou com `-p 1`). Não é uma regressão desta tarefa — é uma característica pré-existente da suíte (todos os pacotes de teste com `DATABASE_URL` apontam para o mesmo banco, sem isolamento por schema/transação). Ao rodar a suíte completa contra um banco real, preferir `go test -p 1 ./...` para evitar falsos negativos por contenção. Reconfirmado nesta tarefa (2026-09-16): `TestAdminUserHandlers_CRUD_HappyPath` falhou só na suíte completa, passou isolado.
- **`COUNT(*) OVER()` perde o total quando a página consultada fica vazia (2026-09-16, paginação do histórico).** A primeira versão de `BackupRunRepo.List` (RN-BACKUP-025) tentou trazer o total de registros na mesma query paginada via `SELECT ..., COUNT(*) OVER() AS total_count ... LIMIT $3 OFFSET $4` — funciona quando a página tem pelo menos uma linha, mas quando `OFFSET` ultrapassa o total de linhas correspondentes, a query retorna zero linhas e não há nenhuma linha para carregar o valor da window function, então o `total` calculado no Go ficava `0` em vez do valor real. Descoberto pelo próprio teste de integração (`TestBackupRunRepo_List_PaginationAndStatusFilter`, caso "page beyond the last returns zero rows and the real total, not an error") rodando contra um Postgres real, antes de o código ser considerado pronto. Corrigido trocando para duas queries separadas: um `SELECT COUNT(*) ...` (sem `LIMIT`/`OFFSET`) mais a query paginada de sempre. **Armadilha para o futuro:** qualquer paginação que precise do total junto com a página não deve usar `COUNT(*) OVER()` acoplado a `LIMIT/OFFSET` — só funciona enquanto a página atual não estiver vazia; usar uma query de contagem separada (mais uma ida ao banco, mas correta em todos os casos, incluindo página além do fim).
- **`docker ps` (sem `-a`) já filtra por "container rodando" — não precisa de um `docker inspect` adicional (2026-09-16, resolução de container por nome parcial).** Ao implementar RN-BACKUP-023 (resolver `containerName` parcial via `docker ps --format '{{.Names}}' | grep`), o check de "container está rodando" que antes usava `docker inspect -f {{.State.Running}} <nome>` (em `server_ssh.go`, `checkDumpTool`) pôde ser eliminado por completo: como `docker ps` sem `-a` só lista containers em execução, uma única correspondência no grep já garante "existe e está rodando" ao mesmo tempo. Simplificou o check para uma única chamada em vez de duas.
- **`performBackup` (`httpapi/handlers/backup.go`) montava o `DumpPlan` antes de abrir a conexão SSH — ordem que teve que ser invertida para resolver o container por nome parcial (2026-09-16).** Diferente do `scheduler/executor.go` (que já conectava antes de montar o plano), o caminho manual de `backup-now` chamava `scheduler.BuildDumpPlan(server, dbPassword)` e só depois `sshclient.Connect(...)`. Como a resolução do container (RN-BACKUP-023) precisa rodar um comando remoto via SSH, isso exigiu reordenar a função: decriptar credenciais → conectar SSH → (se `deploymentMode=docker`) resolver o container → só então montar o `DumpPlan` com o nome já resolvido. **Armadilha para o futuro:** qualquer nova etapa de `BuildDumpPlan` que dependa de uma consulta ao servidor remoto precisa checar a ordem de conexão em **todos** os call sites (`executor.go` e `backup.go` têm históricos independentes e já divergiam nessa ordem antes desta tarefa).

- **Padrão para testar `ExecuteBackup`/`sshclient` de ponta a ponta sem mocks (2026-09-16, teste e2e de redação de slog): montar um servidor SSH real e minimalista dentro do próprio teste (`golang.org/x/crypto/ssh` + `ssh.ServerConfig{NoClientAuth: true}`), não um mock de interface.** `BackupExecutor.ExecuteBackup` chama `sshclient.Connect`/`RunCommand`/`StreamCommand` diretamente (tipos concretos, sem interface injetável) — os mocks de SSH que já existiam em `executor_test.go` (`mockSSHClient`) são código morto, nunca chamados por nenhum teste, e a assinatura nem bate com a real. Para provar algo end-to-end (ex. que o `slog` nunca vaza a senha do banco numa falha remota real, RN-BACKUP-029/RN-BACKUP-027), o caminho barato é: `net.Listen` numa porta livre + `ssh.NewServerConn` aceitando uma conexão + um loop respondendo a canais `"session"`/requisições `"exec"` com stdout/stderr/exit-status configuráveis via `channel.Write`/`channel.Stderr().Write`/`channel.SendRequest("exit-status", ...)`. `internal/sshclient/stream_test.go` já tinha um servidor assim (`startHungSSHServer`, que nunca responde, só para testar cancelamento de contexto) — mas por estar em `_test.go`, não é importável de outro pacote (Go não inclui arquivos de teste ao compilar um pacote para import), então uma variante "com resposta configurável" precisou ser reescrita dentro do próprio pacote `scheduler` (`executor_slog_test.go`, `startScriptedSSHServer`), não reaproveitada por import direto.
- **`repository.StorageTargetRepo.Create` exige que o chamador já preencha `t.ID`** (diferente de `ServerRepo.Create`, que gera `uuid.New()` internamente se `s.ID == ""`) — passar um `StorageTarget{}` sem `ID` falha em runtime com `ERROR: invalid input syntax for type uuid` (a string vazia não é um UUID válido para a coluna `id`). Sempre setar `ID: uuid.NewString()` explicitamente ao construir um `domain.StorageTarget` em teste, como já fazia `claim_and_enqueue_test.go`.
- **GitHub Pages não se auto-habilita automaticamente mesmo com permissão `pages: write` (2026-09-16, deploy do diagrama de arquitetura).** `actions/configure-pages@v5` (com `enablement` padrão `true`) não habilitou o GitHub Pages automaticamente para este repositório na primeira execução do workflow — retornou `HttpError: Not Found` consultando a API de Pages. O workaround documentado por GitHub e a comunidade é habilitar manualmente uma única vez via `gh api --method POST repos/{owner}/{repo}/pages -f "build_type=workflow"` (ou via Settings → Pages → Build and deployment → Source → "GitHub Actions"). Depois disso, o workflow e os deploys subsequentes funcionam normalmente. **Armadilha:** não é um erro do workflow YAML (que está correto), é uma configuração de repositório pré-requisito.
- **Armadilha de ambiente: Alpine containers sem `tzdata` + Go `time.Now()` sem fuso explícito = todas as operações de tempo em UTC (2026-09-17, correção do cron timezone bug).** O bug foi: cron `0 3 * * *` (esperado "3am Brasil") disparava às 00:00 ("3am UTC" = "00:00 São Paulo"). A raiz: `scheduler.NextRunTime(expr, time.Now())` chama `time.Now()` (que retorna a hora local do processo, UTC ou não conforme o SO/container), depois `cron.Next(from)` interpreta "3am" no `time.Location` que `from` já carrega — neste caso UTC. Solução: (1) fixar no código: `time.LoadLocation("America/Sao_Paulo")` + `from.In(loc)` antes de `cron.Next()`, não dependendo da timezone do processo. (2) Embutir a base IANA de fusos: `import _ "time/tzdata"` em ambos os entrypoints (`cmd/api/main.go`, `cmd/worker/main.go`), porque Alpine não instala `tzdata` por padrão e `LoadLocation` falharia em runtime sem ele. (3) Consistência operacional: `ENV TZ=America/Sao_Paulo` em todos os containers que tocam em agendamento, para que logs/slog também mostrem horário de São Paulo, não UTC — apesar da defesa de código (item 1) já garantir o comportamento certo independente da env var. **Lição:** qualquer operação que precise de horário Brasil não pode confiar só em `time.Now()` ou `ENV TZ`, precisa forçar a location no código.

- **Versionamento automático de imagens Docker (2026-09-17, script `build-images.sh`).** Decisão do usuário: o script lê `prod-version` (arquivo versionado), incrementa patch (ex.: `v1.0.0` → `v1.0.1`), builda 3 imagens Docker e as faz push para `c3t4r4/backapeando` com tags duplas (`backend-v1.0.1` + `backend-latest`, etc.), e só então escreve a nova versão em `prod-version` e commita — tudo atomicamente, falha em qualquer etapa cancela o commit. **Convenção:** cada imagem recebe um prefixo no nome da tag (`backend-`, `worker-`, `frontend-`) + versão (formato `vMAJOR.MINOR.PATCH`) + e também uma tag `-latest`. Git login é manual (`docker login` antes de rodar o script). Escrita de `prod-version` é atomicizada (temp file + `mv`, não simples redirect) para evitar truncação em caso de kill/power-loss. **Lição:** qualquer versionamento que serialize o estado em arquivo versionado e faça push de artefatos deve garantir que o arquivo só é atualizado depois do push, nunca antes — garante que commits refletem exatamente o que foi publicado.

- **Incompatibilidade de `depends_on` em Docker Swarm (2026-09-17, fix `docker-stack.yml`).** Docker Swarm (`docker stack deploy`, usado pelo Portainer) **não suporta** a sintaxe longa de `depends_on` com `condition:` (ex.: `condition: service_healthy`) — essa sintaxe é só do Compose tradicional. Swarm ignora silenciosamente ou rejeita a chave, deixando sem garantia de ordem de inicialização entre serviços. **Compensação implementada:** (1) `api` e `worker`: removido `depends_on:`, alterado `restart_policy` para omitir `max_attempts` (deixando-o ilimitado), resultando em crash-loop a cada 10s até Postgres/Redis ficarem healthy. Motivo: Go app chama `os.Exit(1)` em `backend/internal/db/migrate.go` (DB) e `backend/internal/auth/ratelimit.go` (Redis) se conexão falhar — não há retry interno, crash-loop é a única rede de segurança. (2) `web`: removido `depends_on: [api]`, deixou `restart_policy` inalterado (max_attempts: 5). Motivo: nginx em `frontend/nginx.conf` usa `resolver 127.0.0.11 valid=10s` + proxy_pass com variable (defers DNS resolution a request-time, não startup), então nginx sobe normalmente mesmo sem `api` estar pronto, requests falham com 5xx até api ficar resolvível, então auto-recover. **Lição:** Docker Swarm e Portainer exigem estratégias de resiliência diferentes de Compose — não depender de ordering declarativo, confiar em retry/backoff do orquestrador (restart_policy unlimited) ou app-level (dinâmico resolver de DNS, não static upstream).

- **Volume nomeado em `/app` sombreia o binário da imagem no Swarm (2026-10-05).** Com `backup_api_app:/app` (e equivalente no worker), o serviço podia mostrar `c3t4r4/backapeando:backend-v1.0.7` enquanto `/api/health` respondia só `{"status":"ok"}` sem `version` e `POST /api/retention-sweep` dava 404. O volume persiste o `/app` da primeira execução; tags novas e `--force` não substituem esse conteúdo. **Regra:** nunca montar volume sobre `/app` em api/worker — binários são imutáveis na imagem. Após remover os mounts do compose: `docker stack deploy`, confirmar Mounts vazios, só então `docker volume rm` dos órfãos.

## Decisões importantes

- Sistema é modelado como operador único (sem MFA, sem múltiplos papéis confirmados, recuperação de senha via CLI no host).
- Worker (`cmd/worker`) é processo separado da API justamente para permitir múltiplas réplicas da API sem duplicar execução de backup (`SKIP LOCKED`).

- Gestão de `admin_users` era 100% CLI (`./api create-admin`/`./api reset-password`) até 2026-09-15 — o usuário confirmou explicitamente expor um CRUD completo via web (`/api/admin-users*` + telas `AdminUsersView`/`AdminUserNewView`/`AdminUserEditView`), com o CLI mantido como fallback, não removido. Duas guardas de segurança novas foram decisão explícita do usuário (não inferência): bloquear autoexclusão e bloquear exclusão do último admin restante (`RN-AUTH-002`/`RN-AUTH-003`). Risco aceito conscientemente: a checagem de "último admin" não é atômica (`Count()` + `Delete()` são duas chamadas separadas) — mantido simples dado o baixíssimo volume de operadores concorrentes deste sistema interno.
- Decisão consciente do usuário: as telas T-11/T-12/T-13 (Administradores) usam componentes shadcn-vue (`ui/table`, `ui/dialog`, `ui/input`, `ui/label`) em vez do Tailwind puro usado por `ServerList.vue`/`StorageTargetList.vue` — mesmo divergindo do padrão visual das demais telas de CRUD do projeto.
- **Limitação de teste conhecida e aceita: `TestAdminUserHandlers_Delete_LastAdminBlocked`** (`backend/internal/httpapi/handlers/admin_users_test.go`) só exercita de fato o bloqueio de "último admin" (RN-AUTH-003) quando o banco de teste compartilhado tem exatamente 1 admin no momento da execução — este projeto não faz reset de schema por teste, então forçar esse estado exigiria apagar contas reais de um banco de dev compartilhado, o que o teste explicitamente recusa fazer (usa `t.Skip` com o motivo). Os outros dois cenários da mesma guarda (autoexclusão bloqueada; exclusão de admin não-último bem-sucedida) são determinísticos e não têm essa limitação.
- **Armadilha de teste com shadcn-vue `ui/dialog` (reka-ui) descoberta nesta tarefa:** `DialogContent` renderiza via `<Teleport>` para `document.body`. `wrapper.find(...)` do Vue Test Utils não enxerga esse conteúdo (fica fora da árvore do componente montado), e `global: { stubs: { teleport: true } }` **não resolve** — o stub de teleport do VTU 2 não repassa o slot quando `disabled=false` (que é o padrão), então o conteúdo simplesmente não renderiza em lugar nenhum. A solução que funcionou: montar com `attachTo: document.body`, aguardar `flushPromises()` (a Presence do reka-ui monta de forma assíncrona) e buscar via `new DOMWrapper(document.body).find(...)`, desmontando (`wrapper.unmount()`) no `afterEach` para não vazar conteúdo teleportado para o próximo teste. Ver `frontend/src/components/BackupRunDetailsDialog.spec.ts`.

- **Decisão do usuário: Sweep resiliente vs. parar-no-primeiro-erro (2026-09-28).** Investigação de bug crítico ("storage não está limpando") descobriu que `retention.Sweep` parava no primeiro erro de `DeleteBlob` e nunca tentava os demais blobs excedentes. Ofereci duas opções: (1) deixar o "fusível de segurança" atual (parar no primeiro erro), apenas melhorar observabilidade do problema, ou (2) tornar resiliente (continuar mesmo com erros, agregar e reportar). Usuário escolheu (2): **Sweep resiliente é a escolha preferida** — um único blob falhando (credencial sem permissão de delete, ou blob preso em transação) não deveria impedir a limpeza dos demais. Implementado com `errors.Join()` — `Sweep` retorna `(partial-success-list, aggregated-error)`, caller decide o próximo passo (retorna como erro ou registra como warning + retorna resultado parcial). Mudança de contrato documentada em código (comentários atualizados) e em `RegrasNegocio.md` (RN-BACKUP-003).

- **Decisão do usuário: Probe de delete obrigatório (2026-09-28).** A causa raiz do bug de retenção travada era credencial de storage sem permissão de delete (SAS token Azure ou IAM key S3 sem o escopo de `delete`) — passava no "test-connection" (que testava só list/read) e depois quebraria o expurgo silenciosamente em produção. Ofereci opção: adicionar `ProbeDelete` ou deixar pra depois. Usuário confirmou: **adicionar `ProbeDelete` a todos os backends** (Azure, S3, Filesystem) para capturar má-configuração cedo. Implementado. Mudança de contrato: interface `storage.Backend` ganha novo método `ProbeDelete(ctx) error`.
